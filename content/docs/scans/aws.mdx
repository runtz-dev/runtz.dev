# AWS scanning

Runtz runs **18 read-only configuration checks** across IAM, S3, EC2/EBS, RDS,
CloudTrail and EKS. In **Cloud → Add cloud → Amazon Web Services**, choose
**Connect through the site** or **Scan with Runtz CLI**. New connections use a
**dedicated IAM user access key**. IAM role onboarding is deferred to a later release.

## Prepare read-only access

Use a dedicated IAM user, without console access, in the account you want to
scan. Download the [Runtz read-only policy](/docs/assets/runtz-aws-readonly-policy.json).
It contains the configuration-read permissions used by the current catalog.

### Via AWS console

1. Open **IAM → Users → Create user** and create a dedicated `runtz-security` user.
2. Under **Permissions → Add permissions → Create inline policy → JSON**, paste
   the downloaded policy. Name it `RuntzReadOnly` and save.
3. Open **Security credentials → Create access key**. Choose the use case that
   matches where you run Runtz. Record the **access key ID** and **secret access key**.
   The secret value is only shown when it is created.
4. Copy your 12-digit account ID and decide which enabled regions to scan.

### Via AWS CLI

Run these commands using an administrator identity authorized to create IAM users
and policies. First confirm the returned account is your intended target. Save
the downloaded policy as `runtz-readonly-policy.json` in the current directory.
If the user name already exists, choose a unique dedicated name consistently.

```bash
aws sts get-caller-identity
aws iam create-user --user-name runtz-security
aws iam put-user-policy --user-name runtz-security --policy-name RuntzReadOnly --policy-document file://runtz-readonly-policy.json
aws iam create-access-key --user-name runtz-security
```

These are setup operations performed by the administrator. The scanner only
reads configuration. See the [AWS access key command reference](https://docs.aws.amazon.com/cli/latest/reference/iam/create-access-key.html).

## Connect through the site

1. Choose your workspace, account ID and enabled regions, such as `us-east-1, sa-east-1`.
2. Follow either setup method, then enter the access key ID and secret.
3. Verify access, name the connection and choose **Connect and start scan**.

Runtz verifies the account and IAM user identity. Root keys and temporary session
credentials are rejected. Key values are encrypted in the Security database and
are never returned in connection metadata. Site connections repeat every 12 hours.
To rotate a key, use **Settings → Cloud → Replace access key**, verify a new scan,
then revoke the old key in AWS. Existing IAM role connections remain readable.

## Scan with Runtz CLI

Install or update [Runtz CLI](/docs/install-cli). Sign in using a token for the
workspace that should receive your results, configure AWS, then scan:

```bash
runtz login
runtz aws config
runtz aws
```

The prompt asks for **account ID**, **access key ID**, **secret access key**,
**regions** and a display name. The secret is hidden while typing. Configuration
is validated before it is saved. On Linux the file is `~/.config/runtz/config.json`
with owner-only permissions; macOS and Windows use their native config directory.
`RUNTZ_CONFIG_DIR` overrides the directory.

Configuration is saved locally. The CLI sends cloud credentials over HTTPS to
Runtz Security for validation and scanning. Private checks run there and this
CLI API does not save credentials. The CLI then uploads evaluated checks, findings
and coverage to your workspace. `runtz aws` opens setup automatically
if AWS is missing in an interactive terminal; `runtz aws config` only configures.

For CI, supply `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `RUNTZ_TOKEN`
through your secret manager. Provide account and regions explicitly:

```bash
runtz aws --account-id YOUR_ACCOUNT_ID --regions us-east-1,sa-east-1 --high-threshold 1
```

The terminal prints progress and a link to **Cloud → Amazon Web Services**.
Results are sent before an enabled severity gate returns exit code `3`.
Update local keys with `runtz aws config`. CLI scans run when you execute or
schedule the command; they have no automatic Runtz server schedule.
A scope connected through the site must be disconnected before switching to CLI.

## Coverage

Global IAM/account checks run once. Regional checks evaluate the selected regions;
other regions remain outside coverage. Missing permissions and unevaluated fields
appear under **Checks**, not as passes. A failed scan preserves previous results.

S3 public-access-block checks evaluate controls, not proof of public bucket access.
Security-group checks evaluate configuration, not effective reachability. RDS
cluster/replica-managed backups and organization/shadow CloudTrail trails require
separate review. AWS Organizations, ECR and disk-content scanning are outside scope.

## Remove a connection

In **Settings → Cloud**, remove the connection or CLI results. This does not delete
the AWS IAM user or revoke its keys. Revoke unused keys in AWS separately.

## Operator setup

Deploy the AWS-capable Runtz Security service before using site connections.
Direct-key connections do not require a central Runtz AWS identity. See the
[operator guide](https://github.com/runtz-dev/runtz-security/blob/dev/docs/aws-setup.md).
CLI scanning requires the public Security API, authenticated with your workspace
token, and uploads evaluated results through the engine.
